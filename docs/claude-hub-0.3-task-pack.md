# 0.3 任务包：发现、计划、批准与安全写入

## 交付目标

Agent 可以安全地发现模型、生成确定性建议和脱敏变更计划；用户明确批准后，系统才对 Standalone 或受限 Companion 字段执行原子写入。任何不确定的外部状态都必须阻止写入，而不是猜测。

## 前置条件

- 0.1、0.2 Exit Gate 已通过。
- 先明确当前 canonical runtime 与旧 `src/claude_hub` 产品线的关系；不得把旧堆叠 PR 当作基线。
- #71 的 capability profile、认证隔离和协议统一层必须作为架构门槛评估；不允许把能力判断散落到各 CLI/GUI 分支。

## 阶段一：发现与测试（#19-#24）

### 0.3-A URL 规范化与 SSRF 边界（#19、#20）

- 目标：规范化 Provider URL，生成同源模型发现候选，并阻止私网、重定向和 DNS rebinding 绕过。
- Red：同一 URL 多种写法产生不同策略，或检查地址与实际连接地址不一致。
- Green：canonicalization、解析、peer pin、redirect policy 有单一 owner；策略函数不自行联网。
- 验收：默认/显式端口、IPv4/IPv6、私网、重定向、DNS rebinding、TLS 名称测试。
- 不做：自动发现后直接保存或切换 Provider。

### 0.3-B 模型列表、缓存与分层检查（#21-#23）

- 目标：区分 DNS、TLS、鉴权、模型列表和真实推理可用性；缓存明确 stale/verified。
- Red：缓存旧结果冒充当前验证，或者 DNS/TLS/鉴权失败被统一成“模型不可用”。
- Green：每层有稳定结果和错误归因；缓存刷新失败不伪装成功。
- 验收：未命中、命中、过期、刷新失败、鉴权失败、列表损坏 fixture。
- 不做：默认发送计费请求。

### 0.3-C 显式计费推理 smoke test（#24）

- 目标：只有用户明确确认可能计费后，才执行最小推理验证。
- Red：测试默认发真实请求，或计费风险没有进入用户可见确认。
- Green：默认不执行；确认、取消、失败和费用提示均有可观察记录。
- 验收：fake upstream 完整测试；真实渠道只做人工、脱敏、可撤销 smoke test。
- 不做：把 smoke test 当长期健康监控。

## 阶段二：建议、计划与 Standalone apply（#25-#29）

### 0.3-D 模型用途槽位与能力适配（#25、#26）

- 目标：按 Provider capability 和模型元数据生成确定性建议，不用模型名子串猜测能力。
- Red：未知模型被当成已知模型，或全局开关代表所有 Provider。
- Green：建议输入、规则来源和 unknown 状态可审计；同样输入得到稳定结果。
- 验收：已知、未知、冲突、空能力、非标准 model id 矩阵。
- 不做：直接修改任何 Store。

### 0.3-E 脱敏变更计划与字段 diff（#27）

- 目标：生成字段白名单、稳定 digest、可解释 diff 的计划。
- Red：计划包含 Key、完整私有 URL、不可验证的隐式修改，或同一输入 digest 不稳定。
- Green：只允许模型字段；目标、fingerprint 和 warning 的公开边界明确。
- 验收：无变化、单字段、多字段、未知字段、脱敏和 digest 稳定性测试。
- 不做：计划生成即写入。

### 0.3-F 一次性人工批准（#28）

- 目标：批准记录绑定 plan digest、目标和短 TTL，严格单次消费。
- Red：批准可跨计划重放、过期仍可用、失败后状态不清。
- Green：批准是 sole consumer；消费顺序和失败后的重新批准要求明确。
- 验收：命中、过期、错误 digest、重复消费、并发消费测试。
- 不做：跨进程持久化批准，除非另有安全设计。

### 0.3-G Standalone CAS apply（#29）

- 目标：批准后以 CAS、锁、原子替换和 readback 完成 Standalone 写入。
- Red：其他进程修改期间覆盖新值，或写入失败留下半成品。
- Green：提交前后版本、锁和 readback 规则明确；失败不会伪装成功。
- 验收：并发修改、进程中断、权限错误、旧版本、readback 不一致测试。
- 不做：没有批准的写入。

## 阶段三：可逆全局默认（#30-#31）

- 目标：只有用户显式选择时才设置全局默认，并能在不覆盖外部修改的前提下恢复。
- 依赖：0.3-F、0.3-G。
- Red：全局默认被隐式修改，恢复覆盖了外部新修改，或回滚不可解释。
- Green：全局变更有备份、CAS、恢复条件和清晰提示。
- 验收：显式确认、取消、外部修改、恢复冲突、备份损坏测试。
- 不做：启动时自动设为全局默认。

## 阶段四：Companion 受限安全写入（#32-#35）

### 0.3-H 生命周期与能力 preflight（#32）

- 目标：写入前证明 CC Switch 停止、schema/能力兼容、目标仍匹配计划。
- Red：只检查一次后长时间等待，进程状态变化仍继续写入。
- Green：preflight 与提交临界区的生命周期合同明确；不满足条件立即 fail-closed。
- 验收：进程在检查后启动、schema 变化、能力变化、目标变化、代理 takeover fixture。
- 不做：强制杀掉用户进程。

### 0.3-I 备份与 CAS 修改模型字段（#33、#34）

- 目标：只修改批准的模型字段，先备份，再 CAS 提交，能识别外部变化。
- Red：URL、Key、current Provider 或代理开关被顺带改动；外部变化被覆盖。
- Green：字段白名单、备份、CAS、readback 和恢复边界都有测试。
- 验收：非目标字段变化、并发写入、中断、备份恢复、readback 失败测试。
- 不做：对活动 Provider 或运行中的 CC Switch 直接写内部 DB。

### 0.3-J live settings 与 proxy takeover 恢复（#35）

- 目标：同步和恢复当前 live settings 时保留所有权边界，区分 Hub 自己的临时状态和外部状态。
- Red：恢复操作覆盖外部修改，或把临时凭证/完整 URL写入审计。
- Green：所有权、恢复快照、失败重放和审计字段可证明。
- 验收：proxy takeover、外部修改、异常退出、恢复冲突和脱敏审计测试。
- 不做：无条件接管 CC Switch 控制面。

## 0.3 Exit Gate

- 发现、计划、批准、写入是四个可独立观察的阶段。
- 没有批准不能产生写入副作用；批准不能跨计划或重复消费。
- Standalone 与 Companion 使用同一套计划/批准语义，但各自拥有正确的存储 owner。
- Companion 只修改批准的模型字段，所有其他字段保持只读。
- CAS、备份、readback、恢复和生命周期竞态都有相邻测试；平台或真实 CC Switch 未验证项明确列出。
