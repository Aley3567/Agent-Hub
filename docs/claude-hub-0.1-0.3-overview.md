# Claude Hub 0.1-0.3 交付总览

## 文档性质

这是交给执行 agent 的路线总览，不是当前实现状态，也不是“已经完成”的证明。Issue #4 是产品设计来源；旧 PR 已关闭，不能把旧 PR 的代码或历史 CI 当作当前主线验收证据。

本批次只覆盖 0.1、0.2、0.3。每个版本都必须沿一条可运行路径纵向完成，不能先堆数据库、CLI、GUI，最后才集成。

## 产品边界

- Companion 模式：CC Switch 是 Provider、凭证和当前配置的唯一真相来源。
- Standalone 模式：没有 CC Switch 时，使用独立 Profile、系统凭证库和隔离会话。
- Agent 可以 detect、list、inspect、discover、test、plan。
- apply 必须绑定一次性人工批准；自动发现只产生建议或计划，不静默写入。
- Key 不进入 argv、环境变量、Agent JSON、日志、审计或错误正文。
- Companion 第一版只允许修改模型字段；URL、Key、current Provider、代理开关保持只读。
- CC Switch 生命周期、schema 或能力不明确时默认 fail-closed，并允许用户显式选择 Standalone。

```text
  -> 0.3 发现、计划、批准、写入
```

## 统一任务规则

1. 一次只领取一个任务卡；任务卡必须有明确 owner module 和完成证据。
2. 先把 Issue 转成可观察行为，分开记录事实、假设和未知。
3. 在真实 interface 写 Red 测试；测试应观察公开行为，不断言私有调用次数。
4. 实现最小完整语义使其 Green，再补相邻边界矩阵。
5. 涉及 CC Switch、凭证、并发、持久化、网络或真实 Claude 运行态的任务，必须说明未执行的环境证据。
6. 防御性围栏不能冒充根因修复；每个围栏都要写明它独立防止的风险。
7. 任务完成报告必须使用：观察事实、根因与证据、修改规则及 owner、检查结果、真实运行验证、剩余不确定性。

## 统一提交门

一个版本只有同时满足以下条件，才能进入下一版本：

- 该版本任务卡全部完成或被明确判定为不做；
- 关键路径可从用户入口运行到可观察结果；
- 原症状测试、相邻边界测试和禁止行为测试通过；
- 全量测试通过，或剩余失败有明确归因且不被伪装为成功；
- 外部环境未验证时，状态只能写“代码完成，运行态未验证”；
- 交付 agent 已提供 commit、测试命令、输出摘要和未解决风险。
