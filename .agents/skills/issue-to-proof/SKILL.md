# Issue To Proof

目标是形成可证伪的因果解释、由正确 module 拥有的稳定规则，以及与声明强度匹配的验证证据。不要把流程完成、代码改动或测试绿灯本身当作问题已经解决。

## 调整深度

仅当故障可稳定复现、原因已有直接证据、规则只有一个明确所有者，且不涉及外部环境、并发、持久化、安全或重放时，使用短路径：复现 -> 单个 Red/Green -> 原症状 -> 相关测试 -> 报告。

其余情况使用完整流程。若用户只要求诊断，停在因果解释和下一项区分性实验，不实施修复。

## 1. 建立问题契约

先把报告翻译成外部可观察行为，不接受报告中的根因猜测作为事实。记录：

- 实际症状、输入、时间、环境和错误原文；
- 期望行为与明确不做的行为；
- 成功判据，以及哪些判据必须在真实运行态证明；
- 当前的 `事实 / 假设 / 未知`。获得新证据时移动条目，不混写证据等级。

## 2. 有界侦察

读取 `AGENTS.md`、`CLAUDE.md`、相关设计文档、邻近测试、issue 正文，以及最相似的历史 issue 或提交。只追踪能解释症状的最窄链路：

```text
输入与配置 -> 解析与规范化 -> 状态与策略 -> 外部副作用 -> 输出 -> 持久观测
```

沿链路检查 interface 和 seam，特别关注：规则所有权、信任输入、身份、并发、持久化、隐私、协议、提交点，以及提交后是否仍可安全重放。侦察的产物是执行路径和责任图，不是读过的文件清单。

## 3. 建立真实基线

优先复用现有测试、命令、日志、trace、真实脱敏载荷或 benchmark。无法复现时，保存最强的失败证据并明确置信度限制。

只提出足以决定下一步探针的竞争假设。每次选择成本最低、区分度最高的实验，一次只改变一个变量。根因必须同时具备：

1. 能解释已观察现象的机制；
2. 能排除主要竞争解释的证据；
3. 指出缺失或错误规则的所有者；
4. 给出修复后应改变什么的反事实预测。

不要用调用栈最后一行、HTTP 状态码或异常文本代替根因。

## 4. 对复发做逃逸分析

找到最近的同类修复，检查它当时声称保护的规则和实际测试。把复发分类为：

- **原样回归**：同一机制重新失败；检查契约是否被绕过、测试是否失效或未执行。
- **邻路复发**：另一条路径重复解释同一规则；把知识收归唯一所有者。
- **新变体复发**：新的输入绕过样本特判；把样本规则提升为稳定分类或 invariant。
- **运行态复发**：测试环境与真实路径不同；补真实 fixture、集成路径或环境验证。

在解释“为什么旧修复没有阻止本次问题”之前，不开始新的语义修复。

## 5. 写出因果根因

使用能被证据反驳的句式：

```text
当 <条件> 时，<module> 在 <seam/phase> 将 <事实> 错误解释为 <含义>，
因为 <稳定规则> 缺失、错误或有多个所有者，导致 <可观察结果>。
证据是 <区分性实验>；若判断正确，修改后 <反事实预测> 应成立。
```

若根因描述依赖本次特有的域名、状态码、字段名或用户样本，继续寻找它代表的稳定类别。

## 6. 设计耐久修复

- 分开记录**根因修复**与**防御围栏**。围栏必须说明独立风险，不能冒充根因修复。
- 把规则放进拥有所需知识和责任的 module，使相关调用路径经过同一 interface。
- 对跨路径或共享语义，至少比较两个修复位置。优先选择能减少重复知识、缩小 interface、提高 locality 的位置。
- 只有在消除真实重复、形成真实 seam 或匹配现有模式时才增加抽象。不要为了流程感创建新实体。
- 说明允许行为、禁止行为、错误模式，以及 side effect 前后不同的 retry/replay 语义。

## 7. 纵向实现

1. 在最近的真实 interface 写一个行为测试，使原症状因预期机制变红；若不能先写测试，说明原因并保留可重复的失败命令或载荷。
2. 用一个 tracer bullet 打通最小端到端行为。
3. 实现让该行为变绿的最小完整语义，不提前铺设猜测性能力。
4. 每次增加一个相邻行为并完成一次 Red -> Green。
5. 全绿后再重构，将重复知识收归所有者；不要在 Red 状态重构。

测试通过公开 interface 观察结果。避免 mock 私有协作者、断言内部调用次数，或一次性批量编写基于想象的测试。

## 8. 证据阶梯

按风险选择适用层级，并明确未执行项：

1. **原症状**：同一输入和路径不再失败；
2. **反事实**：修复前测试确实变红，或撤销关键规则会重新失败；
3. **相邻矩阵**：默认/显式、各协议路径、成功/失败、合法/损坏等相关维度；
4. **禁止行为**：安全、因果、身份、提交和重放边界没有被放宽；
5. **仓库检查**：focused tests、全量测试、`git diff --check`，以及相关静态或安全检查；
6. **真实运行**：使用匹配的客户端、配置、网络、上游或并发条件；
7. **可观测性**：持久证据能解释实际选择、phase、所有者和结果，且不泄漏敏感数据。

全量测试只证明测试模型内的行为。外部环境或真实载荷触发的问题，在第 6 层完成前不得报告为“已验证修复”。

## 9. 交付与沉淀

报告必须包含：

```text
观察事实：
根因与识别它的证据：
修改的稳定规则及其所有者：
原症状和检查结果：
真实运行验证：
剩余不确定性：
完成状态：已诊断 / 代码完成，运行态未验证 / 已验证
```

一次性事实留在 issue 或证据文档；变化状态只进入队列；稳定行为进入 module interface 和回归测试。只有重复或可测量的失败才提升为 `AGENTS.md` 规则，避免把事故样本堆成永久提示词。
